# Architecture

Workspace: `ros2_ws/src/`, three packages.

## `mocap_bridge` (C++, `ament_cmake`)

Wraps the NatNet client from [mocap_subscriber](https://github.com/lgkimjy/mocap_subscriber), pulled in as a git submodule at `third_party/mocap_subscriber/` (built via `add_subdirectory`, so it tracks a pinned commit — bump the submodule and commit the pointer to pick up upstream changes) and publishes `geometry_msgs/PoseStamped` per tracked rigid body on `mocap/<name>/pose`. Builds a `mocap_subscriber::NatNetConfig` directly from ROS params (`server_address`, `local_address`, `use_multicast`, `command_port`, `data_port`, `rigid_body_ids`, `rigid_body_names` — the last two are matched by position, so tracking multiple objects means extending both lists together) rather than reading `mocap_subscriber`'s own file format. Polls `NatNetClient::latestPoseById()` on a timer and skips publishing when `isPoseFresh()` is false rather than publishing stale poses.

## `umi_recorder` (Python, `ament_python`)

- `camera_stream.py`'s `CameraStream` owns one RealSense camera end-to-end: opens it directly via `pyrealsense2` on its own background thread (`_run`), bypassing the `realsense2_camera` ROS node — that ROS wrapper was measured to degrade from ~30fps to ~5-8fps within seconds under this exact workload (config, resolution, CPU near-idle), while a raw `pyrealsense2`/`librealsense2` pipeline with the identical stream config sustains a steady ~30fps indefinitely. Uses `rs.align(rs.stream.color)` to align depth to color; no point cloud is computed. Before `pipeline.start()`, `_wait_for_device()` polls `rs.context().query_devices()` for the configured serial and logs a warning + retries every 2s if it's missing, rather than letting `pipeline.start()` block forever with zero feedback (a real failure mode if a serial is wrong or a camera is unplugged). Immediately after `pipeline.start()`, reads `first_depth_sensor().get_depth_scale()` and converts every depth frame to millimeters using that scale before colorizing or recording — depth scale (meters/raw-unit) is camera-model-specific (e.g. ~0.001 on a D435i, ~0.0001 on a D405) and assuming millimeters unconditionally silently produced 10x-wrong depth on a D405. Every depth frame also runs through librealsense's standard denoising pipeline — `disparity_transform(True)` → `spatial_filter()` → `temporal_filter()` → `disparity_transform(False)` — applied to both the live preview and the recorded bag (deliberately no hole-filling filter: that would extrapolate depth for pixels with no real return, and a policy shouldn't train on fabricated depth). `temporal_filter` keeps internal state across frames, so one filter chain is created per `CameraStream` and reused for the camera's lifetime, never recreated per-frame.
- `recorder_node.py`'s `RecorderNode` owns up to `MAX_CAMERAS` (4) `CameraStream`s, built from parallel `camera_names`/`camera_serials`/`camera_widths`/`camera_heights`/`camera_fps`/`camera_max_depth_m` ROS params (all matched by position — same convention as `mocap_bridge_node`'s `rigid_body_ids`/`rigid_body_names`), rejecting more than 4 cameras or any length mismatch across those lists at startup with a clear `ValueError`. Resolution/fps/max-depth are per-camera (not shared) specifically to support mixed rigs, e.g. a close-range D405 (usable range roughly 7-50cm) alongside a wider-range D435i (30cm-3m+) with different `max_depth_m` each.
- Subscribes to one or more mocap bridge `PoseStamped` topics over ROS — `pose_names`/`pose_topics` ROS params, matched by position (same convention as `camera_names`/`camera_serials`), one entry per tracked UMI device (e.g. two grippers: `pose_names: ["right_hand", "left_hand"]`, `pose_topics: ["/mocap/UMI_HandRight/pose", "/mocap/UMI_HandLeft/pose"]`). Each `pose_topics[i]` must match `/mocap/<rigid_body_names[j]>/pose` from `mocap_bridge_node`'s config for the corresponding rigid body. All subscriptions use `qos_profile_sensor_data` (best-effort) to match `mocap_bridge_node`'s `SensorDataQoS` publisher — a reliable subscriber (rclpy's default from a plain integer queue depth) never connects to a best-effort publisher in DDS, so this must stay best-effort or a topic silently stops delivering messages with no error. Each device gets its own `MutuallyExclusiveCallbackGroup` (so one device's callback can't delay another's), its own trajectory buffer (`self._trajectories[name]`), and is recorded under its own bag topic (`self._pose_topics[name]`, the literal topic string, not `pose_names[i]`) — `RecorderNode._make_pose_callback(name)` returns a closure bound to that device's name rather than one shared callback branching on the message's topic.
- Runs a Flask app in a background thread (started from `Node.__init__`) alongside a `MultiThreadedExecutor` on the main thread for the pose subscriptions. `/cameras` lists configured camera names; `/video_feed/<name>` and `/depth_feed/<name>` are MJPEG generators, one pair per camera, each blocking on that `CameraStream`'s own `threading.Condition` (`color_ready`/`depth_ready`) instead of polling on a fixed timer — each new frame calls `notify_all()`, so a stream pushes a frame exactly when one arrives. `/depth_feed/<name>` colorizes with `cv2.COLORMAP_JET`, clipped/normalized against `max_depth_m` (near = bright, beyond `max_depth_m` or no-return = dark/black) — see `CameraStream._handle_depth`.
- `/pose_devices` lists configured pose device names (mirrors `/cameras`). `/trajectory` returns the last `MAX_TRAJECTORY_POINTS` (20) pose points per device as JSON keyed by name, e.g. `{"right_hand": [...], "left_hand": [...]}`, each point `{x,y,z,qx,qy,qz,qw}`. `templates/index.html`'s `loadTrajPanels()` fetches `/pose_devices` on load and creates one independent Three.js scene/renderer per device (`createTrajectoryView()` factory, not a single shared scene) — each panel renders a 3D trail with a small dot per sample (visible even for sub-millimeter motion) plus an `AxesHelper` orientation gizmo at the current pose, rotated by its quaternion — not a flat 2D projection. `pollTrajectory()` dispatches each device's points to its own view by name.
- `/config` returns `{name: {max_depth_m, is_exo}}` per camera so the frontend can label each depth panel's range without hardcoding it. The frontend fetches `/config` then `/cameras` on load and renders one color+depth panel pair per name (`loadCameraPanels()` in `index.html`), so panel count and per-panel labels follow config with no template changes needed.
- Record/Stop (`/record`, `/stop` POST endpoints) toggle recording; `RecorderNode.start_recording`/`stop_recording` call `CameraStream.set_recording()` on every configured camera and reset every pose device's trajectory buffer. Each `CameraStream` writes its own topics into the shared `EpisodeBagWriter` (`bag_writer.py`, a thin `rosbag2_py.SequentialWriter` wrapper) — namespaced by camera name, e.g. `/<name>/color/image_raw`, `/<name>/aligned_depth_to_color/image_raw` — alongside each pose device's own topic, wrapped into `sensor_msgs/Image` via `cv_bridge.cv2_to_imgmsg` (raw depth in millimeters, not the colorized visualization). Each camera also writes a `/<name>/color/camera_info` `sensor_msgs/CameraInfo` message once per recording (real intrinsics queried from the color stream's `VideoStreamProfile` at pipeline start — `CameraStream._build_camera_info`), so a bag is self-contained for anything needing real fx/fy/cx/cy downstream (e.g. RGBD odometry). One bag per episode is fully self-contained and time-synchronized on ROS-clock timestamps across every camera plus every pose device.
- `CameraStream._run` is a two-level retry loop: the outer loop calls `_wait_for_device()` then `_run_pipeline()`, and any exception from `_run_pipeline()` (device unplugged, driver error) is caught, logged, and retried after a 2s backoff rather than permanently ending that camera's thread. Inside `_run_pipeline()`, a single `wait_for_frames()` timeout (`RuntimeError`) is treated as transient and the loop just continues — only an exception outside that inner try/except tears the pipeline down for a full reconnect. This matters because `CameraStream`s are fully independent: one camera failing (wrong/missing serial, mid-session disconnect) must never affect any other configured camera, the web UI, or the pose subscription.

Both nodes' parameters live together in one file, `umi_recorder/config/umi_data_collection.yaml`, as separate `mocap_bridge_node:`/`umi_recorder_node:` top-level sections (ROS 2's standard multi-node YAML params format — each node only reads its own section, so passing the whole file to both is intentional, not a bug). `launch/umi_recorder.launch.py` brings up `mocap_bridge_node`, `recorder_node`, and `exo_pose_bridge_node` (no `realsense2_camera` node — the camera is owned exclusively by `recorder_node`'s pyrealsense2 pipeline, and only one process can hold the USB device at a time), and exposes the config file as a single launch argument (`umi_config`).

## Exocentric camera + `exo_pose_bridge` (human torso tracking)

`RecorderNode` optionally owns one more camera beyond the `MAX_CAMERAS`-capped `camera_*` lists: an **exocentric** camera (e.g. a D435i facing the human operator, not gripper-mounted), configured via `exo_camera_name`/`exo_camera_serial`/`exo_camera_width`/`exo_camera_height`/`exo_camera_fps`/`exo_camera_max_depth_m`. Leaving `exo_camera_name` empty disables it. It's not subject to the 4-camera cap because it serves a different purpose — tracking human torso motion to map to linear base motion — and is added to the same `self._cameras` dict as the gripper cameras, so it gets a UI panel, MJPEG routes, and bag recording for free via the exact same `CameraStream` code path.

Unlike the gripper cameras, the exo camera's color frames also need to reach a separate process live (for pose detection), not just the bag when recording. `CameraStream` gained an opt-in `publish_live=True` constructor param for this: it creates a `sensor_msgs/CompressedImage` publisher (topic `/<name>/color/image_raw/compressed`) and publishes every color frame regardless of recording state. This is deliberately **not** a raw `sensor_msgs/Image` publisher — publishing raw 640x480 bgr8 frames (~0.9MB each) at 30fps through rclpy/DDS measured only ~3-5fps actually delivered even with the subscriber's CPU barely loaded, the same class of ROS-transport overhead that got `realsense2_camera` dropped from this project (see the Notes section below), just triggered by a different code path. Publishing the JPEG bytes `_handle_color` already computes for the MJPEG preview (no extra encoding cost) cut message size ~20x and restored a steady 30fps end-to-end.

**`exo_pose_bridge`** (Python, `ament_python`) is a separate ROS node (package `exo_pose_bridge`, executable module `exo_pose_bridge.pose_node`) that subscribes to the exo camera's compressed color topic, runs MediaPipe Pose (the `tasks.vision.PoseLandmarker` API — MediaPipe 1.x dropped the older `solutions.pose` API), and publishes:
- `/<exo_camera_name>/torso_pose` (`geometry_msgs/PointStamped`) — normalized image coordinates (x, y in [0, 1]), the average of the shoulder-midpoint and hip-midpoint landmarks (BlazePose indices 11/12 shoulders, 23/24 hips). **Not a metric position** — depth back-projection was deliberately left out for simplicity; add it in post-processing against the recorded bag if a real XYZ is needed later, the same way `rgbd_odometry` post-processes bags rather than computing everything live.
- `/<exo_camera_name>/pose_overlay/image_raw/compressed` (`sensor_msgs/CompressedImage`) — the color frame with the detected skeleton drawn directly via `cv2.line`/`cv2.circle` (not MediaPipe's own `drawing_utils`, which imports `matplotlib` — see below). Not recorded into the bag (derived from data that's already recorded: color + torso_pose).

`RecorderNode` subscribes to both: `torso_pose` is recorded like any other topic when recording is active and exposed live via a `/torso_pose` HTTP endpoint; the overlay feed is served as MJPEG via `/pose_overlay_feed` and shown as the exo camera's "Color + pose" panel in the web UI (`index.html`'s `loadCameraPanels()` branches on `/config`'s per-camera `is_exo` flag to swap in the overlay feed and a torso-position text readout instead of the plain color feed).

**Why `exo_pose_bridge` runs in its own venv, as a separate OS process** (not a subprocess call like `rgbd_odometry`, since this needs to run live): `mediapipe` pulls in its own `numpy` (2.x) and `opencv-contrib-python` with no version pin, which conflicts with the numpy this ROS 2 Humble environment pins — the same class of problem `rgbd_odometry` has with `open3d`, except a live pose-tracking path can't afford a per-frame subprocess round-trip the way `rgbd_odometry`'s offline bag post-processing can. The fix: run the whole node inside a dedicated venv (`exo_pose_bridge/.venv/`, gitignored) built with `virtualenv --system-site-packages`, so it still sees `rclpy`/`sensor_msgs`/`geometry_msgs` from the system ROS install (these don't touch numpy's C API, confirmed empirically), with `mediapipe` installed on top.

**`cv_bridge` must not be used inside this venv** — confirmed empirically, not just by inspection: `cv_bridge`'s compiled extension (`cv_bridge_boost.so`) is built against the system's pinned numpy 1.x, and the moment `mediapipe`'s numpy 2.x shadows it in the venv, importing `cv_bridge` crashes with `AttributeError: _ARRAY_API not found`. `exo_pose_bridge/pose_node.py` does its own `CompressedImage` ↔ numpy conversion via plain `cv2.imencode`/`cv2.imdecode` instead.

**`matplotlib` must be installed into the venv explicitly**, not left to fall through to the system copy: `mediapipe`'s top-level `__init__.py` unconditionally imports `mediapipe.tasks.python`, which imports `drawing_utils`, which imports `matplotlib` — and `pip install matplotlib` inside a `--system-site-packages` venv considers the system copy "already satisfied" and won't shadow it, so the system `matplotlib` (compiled against the old numpy) gets imported instead and crashes the same way `cv_bridge` would. Fixed with `pip install --ignore-installed matplotlib` to force a venv-local copy that matches the venv's numpy 2.x.

Because `exo_pose_bridge`'s node can't be launched via `launch_ros.actions.Node` (that assumes the active Python can `ros2 run` the package normally), `umi_recorder.launch.py` invokes it directly via `launch.actions.ExecuteProcess`, calling the venv's own Python binary (`exo_pose_bridge/.venv/bin/python3 -m exo_pose_bridge.pose_node`) and explicitly prepending `exo_pose_bridge`'s source directory to `PYTHONPATH` (since it's not `colcon`-installed into the venv) — `additional_env` replaces rather than extends an existing environment variable, so the ROS-provided `PYTHONPATH` entries (needed for `rclpy` to resolve inside the venv) are preserved by reading `os.environ.get("PYTHONPATH", "")` and joining it in, rather than passing just the new entry. `exo_pose_bridge_node` reads its own `exo_camera_name` param from a separate `exo_pose_bridge_node:` section in `umi_data_collection.yaml` (it is a different ROS node name than `umi_recorder_node`, so params aren't shared automatically — this value must be kept in sync with `umi_recorder_node`'s own `exo_camera_name`) and does nothing if it's left empty, so the node can always be launched unconditionally.

`exo_pose_bridge` needs a `.task` model file (not checked into git, downloaded separately — see Commands section) at `exo_pose_bridge/models/pose_landmarker_lite.task`.

Verified end-to-end against a real D435i: the full pipeline (camera capture → compressed ROS topic → MediaPipe inference → torso_pose + overlay publish, all the way through to the web UI's HTTP endpoints) sustains a steady ~30fps with no CPU bottleneck, launched via the real `ros2 launch umi_recorder umi_recorder.launch.py` entry point (not just manually-started nodes).
